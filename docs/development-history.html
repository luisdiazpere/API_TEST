1 · The starting point

The app began as a working prototype: an Express server that batch-resolves IPs and domains to geolocation data through the ipinfo.io Lite API, with a single vanilla-JS page in front of it. It worked — but it was built for one person's machine, not for exposure. A security review found five issues, the most serious being an API token committed to source control. There was also no persistence of any kind: no accounts, no memory of past lookups.

2 · How the work was developed

The work followed a deliberate sequence, and two ground rules were adopted mid-project and written into CLAUDE.md so they persist for future sessions:

Project rules adopted Never work directly on master — every change gets its own branch (all of this work lives on security-fixes). And never assume — ask first when scope or intent is ambiguous.

That second rule shaped the process visibly. Before any destructive or ambiguous step, the developer (Claude Code, driven by Luis) stopped and asked:

  • "Delete all possible leaks" — files only, or rewrite git history? → Answer: rewrite full history (destructive, so it needed explicit sign-off).
  • ".postman in there" — into .gitignore or into .env? → Answer: .gitignore.
  • Access model — open lookups with history as a login perk, or login required for everything? → Answer: login required, protecting the ipinfo quota.
  • Database — SQLite, a JSON file, or PostgreSQL? → Answer: SQLite, matching the app's single-process scale.

The larger build then proceeded in phases — backend modules first, then server wiring, then the frontend, then end-to-end verification with curl, and finally a live test through an ngrok tunnel before anything was handed over. The UI was not designed ad hoc: a Pencil design file (untitled.pen, kept out of the repo) was parsed programmatically to extract its design tokens, page structures, and exact copy, and the frontend was built to match it.

3 · Security fixes

CriticalHardcoded API token

What: the ipinfo.io token sat as a string literal in src/config.js, committed to git. The fix: the config now reads process.env.IPINFO_TOKEN and throws at startup if it's missing — failing fast beats failing mysteriously on the first API call. The token lives in .env, which is gitignored, and dotenv loads it in development.

Why it matters A secret in source control is compromised the moment the repo is shared, cloned, or pushed — and removing it from the current files does nothing, because git history preserves every version forever. That's why this fix came with a history rewrite (§4).

HighNo rate limiting

What: any client could hammer POST /api/lookup without limit, burning the ipinfo quota and CPU. The fix: express-rate-limit caps the endpoint at 30 requests per minute per IP, answering excess traffic with HTTP 429 and standard RateLimit-* headers.

HighUnbounded uploads

What: multer used memory storage with no size limit — a large upload would be buffered entirely into RAM before any validation ran. The fix: uploads are capped at 1 MB and JSON bodies at 50 KB. For a file of newline-separated IPs with a 50-entry cap per request, 1 MB is already generous.

HighXSS via innerHTML

What: API-sourced values (as_name, country, …) were interpolated straight into row.innerHTML. Data that arrives from any external system must be treated as untrusted — a tainted upstream response would have executed in the browser. The fix: an esc() helper HTML-encodes & < > ", and every dynamic value rendered through innerHTML passes through it — results, error lists, and stat cards alike. (See OWASP's XSS prevention guidance.)

MediumRepository hygiene

.gitignore grew to cover everything that must never be committed: .env (secrets), .postman/ (workspace metadata — it was already tracked, so it was also untracked with git rm --cached), bin/ (the local ngrok binary), *.pen (the design file), and *.sqlite* (the database and its WAL/SHM sidecars).

4 · The git history rewrite

Removing the token from the current files would still have left it readable in the base commit. The repo's full history was therefore rewritten with git filter-branch --tree-filter, running a small Python script against every commit that replaced the literal token with process.env.IPINFO_TOKEN:

FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch --force \
  --tree-filter 'python3 /tmp/scrub_token.py' -- --all

# then: delete refs/original backups, expire reflog, git gc --prune=now
# verify: git log -p | grep <token>  →  no matches
Why this was gated on approval History rewriting is destructive: every commit hash changes (f65bbef → 7cd8159, a8b756b → 6de8822), and any existing clone or remote diverges permanently. Pushing the rewritten master requires a force-push. This is exactly the kind of step the "never assume — ask first" rule exists for; it ran only after an explicit choice. Note that rewriting history does not un-leak a token that was already pushed — the token should still be rotated if the repo was ever public.

5 · The login system

With "login required" chosen as the access model, the entire API sits behind authentication. The design is deliberately boring — proven primitives, no invention:

DecisionChoiceReasoning
Session model Cookie sessions
express-session		 The frontend and API are same-origin (Express serves both), so an httpOnly cookie is invisible to JavaScript — immune to XSS token theft — and logout genuinely revokes access server-side. JWTs would add complexity and lose both properties.
Password storage bcrypt, 12 rounds Deliberately slow hashing blunts offline brute-force if the database ever leaks. Plaintext or fast hashes (SHA-256) are never acceptable for passwords.
Session persistence SQLite store
better-sqlite3-session-store		 Sessions live in the same data.sqlite as the app data, so logins survive server restarts with zero extra infrastructure.
Cookie flags httpOnly, sameSite=lax, 7-day expiry sameSite=lax blocks cross-site POSTs from carrying the session — CSRF protection for exactly the endpoints that mutate state.
Login flow req.session.regenerate() Issuing a fresh session ID at login prevents session-fixation attacks.
Failed login One generic message "Email or password incorrect" — never revealing which was wrong, so the endpoint can't be used to enumerate registered emails.

The secret that signs session cookies (SESSION_SECRET) was generated with openssl rand -hex 32 and lives in .env beside the ipinfo token; config validates both at startup.

6 · The history tracker

Two tables in data.sqlite, created idempotently by src/db.js at startup (WAL mode for concurrent reads, foreign keys on):

users:    id · name · email (UNIQUE, case-insensitive) · password_hash · created_at
lookups:  id · user_id → users (CASCADE) · created_at · requested_count
          · results_json · stats_json · cache_hits · api_calls
Why full results are stored The Pencil design's history rows include a "View Results" button — which is only possible if each session's complete results are stored, not just summary counts. At a maximum of 50 entries per request, a stored session is a few kilobytes; the trade-off is trivially cheap for the feature it enables. The main page re-renders any saved session via /?session=<id>, reusing the exact same rendering code as a live lookup.

Every successful POST /api/lookup saves its full response payload for the logged-in user (wrapped in try/catch so a storage failure can never break the lookup itself). The list endpoint derives what the history page shows: the top continent as the "breakdown" badge, and the cache percentage from cache_hits / (cache_hits + api_calls). Both history endpoints filter by user_id from the session — one user can never read or delete another's rows.

7 · The UI redesign

The frontend was rebuilt to match the Pencil design file exactly — its design tokens were extracted programmatically and became CSS custom properties: background #0F1117, surfaces #1A1D27/#232733, accent #22E5FF, Inter for text and IBM Plex Mono for anything machine-flavored (IPs, ASNs, counts). No framework, no build step — matching the codebase's existing vanilla-JS approach.

PageContents
login.htmlCentered card, lock icon, email + password, "Forgot password?" (stubbed — no backend yet), link to signup. Redirects into the app on success.
signup.htmlName, email, password + confirmation (client-checked match, 8-char minimum enforced both sides).
index.htmlTop bar (brand · "ipinfo.io Lite" badge · account dropdown), textarea + drag-and-drop file zone with a removable file chip, stat cards with a 2×2 metric-tile summary, results table with cached/live badges, collapsible "Parsing Issues" groups with count badges.
history.htmlBreadcrumb top bar, "Search History" table: timestamp + relative time, entry count, region breakdown, cache %, View Results / delete per row, empty state for new accounts.

Shared behavior lives in shared.js: the esc() escaper, the account-menu wiring, and requireSession() — every protected page calls /api/auth/me on load and bounces to the login page on 401. That client-side redirect is a convenience; the real enforcement is server-side on every API route.

9 · How everything was verified

After the build, the full flow was exercised end-to-end with curl against a running server, using a cookie jar to carry the session:

  • ✓ Unauthenticated POST /api/lookup → 401
  • ✓ Register → 201, session cookie issued
  • ✓ GET /api/auth/me → correct user
  • ✓ Authenticated lookup (IPs + domain + private range) → real geolocation data, DNS resolution, bogon detection
  • ✓ GET /api/history → session listed with top region and cache %
  • ✓ GET /api/history/1 → full stored results round-trip
  • ✓ Wrong password → 401, generic error
  • ✓ Logout → session destroyed, /me returns 401

Then the same register-and-lookup flow was repeated through a public ngrok tunnel — which matters because ngrok adds X-Forwarded-For proxy headers that can trip rate-limiter validation. It passed, the test account was deleted, and the URL was handed over for manual testing of the browser flow.

IPINFO_TOKEN=<your ipinfo.io token>
SESSION_SECRET=<openssl rand -hex 32>

Run

npm install
npm start                      # → http://localhost:3000 (lands on login)
./bin/ngrok http 3000          # optional public tunnel

Known follow-ups

  • Rotate the ipinfo token if the repo was ever pushed publicly with the old history.
  • "Forgot password?" is a stub — no reset flow exists yet.
  • UI copy is English (per the design); server error messages remain Spanish.
  • The in-memory ipinfo response cache still grows unbounded between restarts (minor).
  • Set cookie.secure + app.set("trust proxy", 1) when deploying behind HTTPS for real use.
